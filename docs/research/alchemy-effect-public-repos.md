# Public Alchemy + Effect implementations

Checked 2026-09-19 against source code at the linked commits. These projects use the `alchemy` infrastructure package, not the unrelated Alchemy blockchain SDK. The examples are evidence of different working designs, not an Alchemy rule that every application should copy.

## Independent projects

- [backpine/comms-test-harness](https://github.com/backpine/comms-test-harness/tree/0f92f1643fe3853974d246b6c7cddfd68581d0a7) uses an Effect-native Cloudflare Worker for private RPC and another for public HTTP. Its [repository builder](https://github.com/backpine/comms-test-harness/blob/0f92f1643fe3853974d246b6c7cddfd68581d0a7/apps/api/src/repositories/test-record-repository.ts) yields the Alchemy D1 resource and `Cloudflare.D1.QueryDatabase`, then yields `Drizzle.D1` and returns a plain `TestRecordRepository` value. The [RPC Worker](https://github.com/backpine/comms-test-harness/blob/0f92f1643fe3853974d246b6c7cddfd68581d0a7/apps/api/src/backend.ts) yields that repository in init and captures it in `AppRpcs.toLayer` handlers. The [public Worker](https://github.com/backpine/comms-test-harness/blob/0f92f1643fe3853974d246b6c7cddfd68581d0a7/apps/api/src/worker.ts) does the same for its system endpoint but gives `/health` its own dependency-free `HttpApi` group, declared in the [HTTP contract](https://github.com/backpine/comms-test-harness/blob/0f92f1643fe3853974d246b6c7cddfd68581d0a7/packages/contracts/src/http.ts). Its `Database` export is an [Alchemy resource Effect](https://github.com/backpine/comms-test-harness/blob/0f92f1643fe3853974d246b6c7cddfd68581d0a7/packages/db/src/database.ts), not a custom `Context.Service` for a Drizzle client. [Dependencies](https://github.com/backpine/comms-test-harness/blob/0f92f1643fe3853974d246b6c7cddfd68581d0a7/package.json): Alchemy `2.0.0-beta.65`, Effect `4.0.0-beta.102`; last commit in this snapshot was 2026-07-29.

- [kamp-us/phoenix](https://github.com/kamp-us/phoenix/tree/d3b3ac2755367125c668a01ff5b6b163ed30edfe) is a larger Effect-native Worker and makes a different choice. [Database.ts](https://github.com/kamp-us/phoenix/blob/d3b3ac2755367125c668a01ff5b6b163ed30edfe/apps/web/worker/db/Database.ts) declares `Context.Service<Database, D1Database>` and a `DatabaseLive` layer that yields Alchemy's `Cloudflare.D1.QueryDatabase(...)`, then gets its raw binding. [Drizzle.ts](https://github.com/kamp-us/phoenix/blob/d3b3ac2755367125c668a01ff5b6b163ed30edfe/apps/web/worker/db/Drizzle.ts) derives a second service layer from `Database`; feature layers such as [NotificationLive](https://github.com/kamp-us/phoenix/blob/d3b3ac2755367125c668a01ff5b6b163ed30edfe/apps/web/worker/features/bildirim/Notification.ts) `yield* Drizzle` while constructing methods. The [Worker](https://github.com/kamp-us/phoenix/blob/d3b3ac2755367125c668a01ff5b6b163ed30edfe/apps/web/worker/index.ts) resolves `Database` once in init and provides composed layers to its [HTTP router](https://github.com/kamp-us/phoenix/blob/d3b3ac2755367125c668a01ff5b6b163ed30edfe/apps/web/worker/http/app.ts). This is a real example of Effect DI around Alchemy's D1 binding, though it uses D1 rather than Hyperdrive/Postgres. [Version catalog](https://github.com/kamp-us/phoenix/blob/d3b3ac2755367125c668a01ff5b6b163ed30edfe/pnpm-workspace.yaml): Alchemy `2.0.0-beta.77`, Effect `4.0.0-rc.112`; snapshot dated 2026-09-18.

- [brandhaug/b2b-saas-starter](https://github.com/brandhaug/b2b-saas-starter/tree/b8ebb52079f7f23e8c4a571c0e3fc576dab67f6d) uses Alchemy to provision three Workers and their D1 binding in [alchemy.run.ts](https://github.com/brandhaug/b2b-saas-starter/blob/b8ebb52079f7f23e8c4a571c0e3fc576dab67f6d/alchemy.run.ts), but its API is a conventional Cloudflare `fetch` entrypoint, not an Alchemy Effect-native Worker. Its [database service](https://github.com/brandhaug/b2b-saas-starter/blob/b8ebb52079f7f23e8c4a571c0e3fc576dab67f6d/packages/db/src/service.ts) declares `Database` and `RawD1` as `Context.Service`s and provides both via `layerFromD1(env.DB)`. The [capability runtime](https://github.com/brandhaug/b2b-saas-starter/blob/b8ebb52079f7f23e8c4a571c0e3fc576dab67f6d/packages/capabilities/src/runtime.ts) supplies that layer, while the [API router](https://github.com/brandhaug/b2b-saas-starter/blob/b8ebb52079f7f23e8c4a571c0e3fc576dab67f6d/apps/api/src/http.ts) composes separate [handler groups](https://github.com/brandhaug/b2b-saas-starter/blob/b8ebb52079f7f23e8c4a571c0e3fc576dab67f6d/apps/api/src/handlers.ts). It keeps `/health` as liveness and `/ready` as a D1 probe. [Version catalog](https://github.com/brandhaug/b2b-saas-starter/blob/b8ebb52079f7f23e8c4a571c0e3fc576dab67f6d/pnpm-workspace.yaml): Alchemy `2.0.0-beta.77`, Effect `4.0.0-rc.112`; snapshot dated 2026-09-19.

## Alchemy's own example

The official [TanStack RPC + Drizzle backend](https://github.com/alchemy-run/alchemy/blob/4453c9b5006b69c2f23a01c61269d581765802d6/examples/cloudflare-tanstack-rpc-drizzle/src/backend/api.ts) yields `Cloudflare.Hyperdrive.Connect` and `Drizzle.Postgres` in the `RpcWorker` initializer, then captures `db` in a single `TodoRpcs.toLayer({...})`. It does not wrap the Drizzle client in an application `Context.Service`. The package is [Alchemy `2.0.0-beta.79`](https://github.com/alchemy-run/alchemy/blob/4453c9b5006b69c2f23a01c61269d581765802d6/packages/alchemy/package.json), with [Effect `4.0.0-rc.115`](https://github.com/alchemy-run/alchemy/blob/4453c9b5006b69c2f23a01c61269d581765802d6/pnpm-workspace.yaml) in the monorepo catalog at this snapshot. This is the closest official comparison for a Hyperdrive/Postgres RPC API. Its separate [D1 Worker test fixture](https://github.com/alchemy-run/alchemy/blob/4453c9b5006b69c2f23a01c61269d581765802d6/packages/alchemy/test/Cloudflare/D1/fixtures/effect-worker.ts) also resolves a client in init and passes it to [route functions](https://github.com/alchemy-run/alchemy/blob/4453c9b5006b69c2f23a01c61269d581765802d6/packages/alchemy/test/Cloudflare/D1/fixtures/routes.ts).

## What this means for Echo

There is no single demonstrated convention. For a small RPC backend, Alchemy's example and backpine show the simpler init-time resolution plus handler capture. Phoenix shows that `yield* Database` and layered feature services are practical once more consumers need the same binding or a swappable interface. The distinction is not "Effect DI versus Alchemy": all three approaches use Effect layers; they differ in whether the application adds its own database/service tag. This is an inference from these source files, not a documented Alchemy preference.
